01

What consort is

Consort is a deterministic orchestrator for spec-first, test-driven development on live Lakebase branches. A pure state machine (consort-drive) sequences eight stateless LLM role agents through a design lane (spec → architecture → schema → test-list) and a build lane (RED → GREEN → review → refactor), running every build cycle against a real copy-on-write branch of a Postgres database. Human-in-the-loop gates fail closed.

The orchestrator is not an LLM. It reads state from disk, computes the single next action, dispatches one role or opens one gate, records the turn, and writes a snapshot — then loops. Role agents never call each other; every handoff is through files under .consort/.

The gap this fills. The repo has ~17 focused design notes under docs/design/refactor/, each explaining one change. None describes the whole — what every directory owns and how they compose. That missing map is this document; the per-refactor notes become its footnotes.

Read as conceptual bands, foundation upward:

Foundationconfig — the base every module reaches into: .consort layout, path resolution, per-step agent config, schemas.
Engine & lanesorchestrator (the brain), gates (HITL + conformance), pipeline (build-lane state machine).
Domain servicesexperiment, test-list, smells, architecture, intake — the artifact lifecycle.
Substrate & I/Olakebase, deploy, setup, session — talking to Postgres, git, and the world.
Observabilitylogging, telemetry, reports — always-on and fire-and-forget; never in the critical path.

First coupling signal. orchestrator ↔ gates is bidirectional (orchestrator→gates 11 edges, gates→orchestrator 4), as are orchestrator↔session and orchestrator↔telemetry. Bidirectional coupling between the engine and its gate layer is exactly the "which one owns this?" ambiguity that makes a single gate-home hard to point at. First candidate to untangle.

How it operates

One tick of the drive loop. The next action is derived fresh every iteration from on-disk state — there is no persisted next-action pointer, so the same state always yields the same action.

↺  If next.json.awaiting_human === false, loop. If true, stop and surface the decision to the human.

The control signals

  • One pause signal. next.json :: awaiting_human is the sole "the machine needs a person" flag — never reverse-engineered from open gates or action kind (a planning backlog pause has neither).
  • Escalations pre-empt. An unresolved blocking problem (11 smell classes + deploy-verify failure) emits raise-to-hil and halts before anything else.
  • Gates pause, then resume. The five HITL gates — spec, plan, test_list, promote, deploy — pause at approval and auto-resume once approved. State lives in gates.json (atomic) + a human-readable selection-log.md.

The per-story cadence

A feature isn't built then shipped — each story runs the full loop on its own experiment branch, and only accepted stories merge up.

06

Where a fact still has more than one owner

This is the payload for the gate-placement work. Each finding names the fact, its current owners, and the single home it wants. Severity stripe: red = honor-system only (no code enforces it), amber = enforced but in several places, indigo = structural coupling.

Rules that live only in agent prose

Stated in role prompts; caught by an advisory reflect-pass at best; no gate hard-blocks them. An agent that forgets, or a hand-edited artifact, passes.

honor-onlyAC independence

Owner: spec-author.md prose. The spec gate checks the independence field is present, not that the ACs are logically independent.

honor-onlyCross-story AC contradiction

Owner: navigator.md REFLECT via consort-cross-story-context — advisory, routes a revise; no hard stop.

honor-onlyField-contract gap

A NOT-NULL persistence field with no user-facing submit AC. Owner: navigator.md REFLECT — advisory; nothing scans architecture × test-list.

honor-onlyNever weaken an AC · never mock the DB · never delete a test

Owners: navigator.md, driver.md, product-owner.md, test-strategy.md. No gate re-reads the Gate-1 then for drift; no linter catches a mocked DB or a deleted test.

Canon duplicated across skill files

restated ×5The layering rule

Restated in architectural-design-principles, architect-reviewer.md, driver.md, test-strategy.md, and test_layering.py.

Home → one authoritative reference; every agent and the fitness test cite it. (Same pattern for config-in-env and no-mock-DB.)

Resolution & enforcement scattered in code

no single doorWorkspace context (host / profile / instance / database)

Split across scm-utils helpers, provisioning/credentials.ts, and deploy.ts reading .env directly. No single consort-side resolver threads all four.

Home → one resolveWorkspaceContext(projectDir) door.

2 file homesModel / effort config

Read from consort-config.json and legacy agent-config.json; unified only inside project-settings.modelFor().

Home → retire the legacy file; step-manifest agentOptions is the sole home.

4 sitesstory.json conformance

Enforced in spec-sync, artifact-conformance, story-pipeline, and gates/.

Home → one heal-then-check gate (the recent gate-conformance move is the pattern; make it the only site).

3 storesTest-list item status

Lives in test-list.json, cycle records, and per-story views. Cycle records are the truth, but not the single read.

Home → cycle records own it; views derive.

11+ entry pointsArtifact validation

response-formatter (agent-side precheck) and gate-conformance (orch-side gate) validate overlapping artifacts with no documented division of labor, plus 9 *-clean validators.

Home → declare the precheck-vs-gate hierarchy; the gate is the authority.

Structural coupling & fat wrappers

cycleorchestrator ↔ gates (and ↔ session, ↔ telemetry)

Bidirectional imports blur which layer owns the gate decision.

Fix → one direction: gates depend on shared workflow vocabulary (in config), not on the engine.

fat CLIBusiness logic in the bin layer

drive.cli.ts is 1462 lines; ~26 of 47 CLIs lack the isCliEntry guard, so logic can't be imported or tested.

Fix → extract runXxxCli pure functions to the service layer; keep bins thin.

07

Toward single gates

The organizing principle, and the one to hold the mapping work to: one fact = one owner = one door. A recovery path or an invariant that even its author must re-read to follow is too complex — fix by subtraction, by finding the existing common path, not by adding another latch. This table is the starting point, not the plan: each scattered fact and where its single home should be.
